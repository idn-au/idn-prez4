Page anatomy

Design notes only — not part of the production page.

  1. Explicit UI orderRender identity → Record description → identifiers and dates → classification and context → Instantiations. Profile path order does not control this.
  2. Record as page focusThe `rico:Record` remains the page resource. Its `schema:Dataset` type remains visible but does not create a second page section.
  3. Date presentationLead with `rico:expressedDate`; retain qualifiers beside it. Normalized boundaries are secondary machine-oriented detail.
  4. Duplicate predicatesWhere schema.org and RiC-O carry the same value, render one human-facing row rather than duplicate rows.
  5. Instantiation groupingRender each linked Instantiation as a card with its own IRI, identity and fields. Repeat the card for multiple Instantiations.
  6. Linked resource labelsSeries, agents, access concepts and formats remain links. Resolve a label for display, but fetch full linked-resource data only on demand.
  7. FallbacksIf an Instantiation lacks `schema:name`, use `rico:name`, then its identifier, then “Instantiation”. Omit empty optional rows.
  8. Separate pages remainInstantiation IRIs remain navigable. `rico:RecordSet` and `schema:Person` keep their normal object pages and profiles.

This mockup shows one Instantiation. The backend response may contain generic, analogue, digital or derived Instantiation links; the UI groups all four consistently.
